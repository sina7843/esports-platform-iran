# نصب، پشتیبان‌گیری، بازیابی و بازگشت به نسخه قبل

## ۱) نصب (محیط محلی/آزمون)
1. پیش‌نیاز: Node 22.12+، pnpm، Docker. `01-INSTALL-TOOLS.cmd` و `02-SETUP-PROJECT.cmd`.
2. `06-CREATE-LOCAL-ENV.cmd` فایل `.env` محلی را می‌سازد (راز واقعی در مخزن نیست؛ الگو: `.env.example`).
3. `docker compose -f compose.yaml -f compose.local-tools.yaml up -d mongo` ← `pnpm install --frozen-lockfile` ← `pnpm build:libs` ← `pnpm db:migrate` ← `pnpm db:seed` (فقط محلی) ← `pnpm dev:api` و `pnpm dev:worker` و `pnpm dev:web` (سه ترمینال).
4. بررسی: `pnpm check` (typecheck + lint + test + build).

## ۲) محیط‌های جدا
| محیط | تفاوت |
|---|---|
| local/ci | adapterهای dev، ورود توسعه فعال، دادهٔ seed |
| staging | `APP_ENV=staging`: adapter dev ممنوع، ورود توسعه ممنوع، MFA اجباری؛ پیکربندی ناقص → توقف با پیام روشن |
| production | `compose.prod.yaml`: auth + keyfile، rootfs فقط‌خواندنی، بدون پورت پایگاه؛ `TRUST_PROXY=true` پشت لبه داخلی |

آمادگی تولید فقط از `/admin/integrations` (فهرست آمادگی) خوانده شود؛ تا هر ردیف «آماده» نشده تولید باز نمی‌شود.

## ۳) انتشار و بازگشت (rollout / rollback)
- **ساخت**: `pnpm build` + سه image در `.github/workflows/ci.yml`، با tag برابر commit. lockfile پین‌شده.
- **ترتیب انتشار**: (۱) پشتیبان کامل و تأییدشده (بند ۴)؛ (۲) migration سازگار-رو‌به‌جلو: مهاجرت‌ها فقط افزایشی‌اند (ایندکس/کلکسیون/فیلد اختیاری) و با checksum ثبت می‌شوند، پس نسخه قدیمی با پایگاه جدید کار می‌کند؛ (۳) worker جدید؛ (۴) api جدید یکی‌یکی؛ (۵) web.
- **بازگشت**: image قبلی را دوباره بالا بیاورید؛ چون migrationها افزایشی‌اند نیازی به برگرداندن داده نیست. اگر migration مخرب در آینده اضافه شود باید جفت «برگشت» و آزمون داشته باشد و فقط با بازیابی پشتیبان بازگردانده شود.
- **ترتیب بازگشت**: web ← api ← worker. پس از بازگشت: `GET /api/v1/health/ready` و `/ops/outbox` (صف بدون dead-letter جدید).
- انتشار عمومی واقعی (دامنه، گواهی، لبه) به‌دست مالک و خارج از دامنه این مخزن است؛ دستور و artifactها آماده و قابل بررسی‌اند.

## ۴) پشتیبان‌گیری (OPS-004)
- **ماهیت**: dump منطقی رمزشده (AES-256-GCM + gzip) از همه کلکسیون‌ها و فایل‌ها، همراه فهرست ایندکس‌ها و `manifest.json` با HMAC. هر مجموعه در پوشه `bak_<زمان>` است.
- **دامنه خرابی مستقل**: `BACKUP_TARGET_DIR` باید روی دیسک/میزبان دیگر باشد؛ داخل `DATA_DIR` رد می‌شود. کلید `BACKUP_ENCRYPTION_KEY` (حداقل ۳۲ نویسه) جدا از پشتیبان‌ها نگهداری شود؛ بدون آن بازیابی ممکن نیست.
- **زمان‌بندی**: worker هر `BACKUP_INTERVAL_MINUTES` (پیش‌فرض ۱۰) پشتیبان می‌گیرد و فقط `BACKUP_KEEP` نسخه آخر را نگه می‌دارد. **RPO بدترین حالت = فاصله + مدت اجرا** و باید زیر ۱۵ دقیقه بماند؛ اگر مدت اجرا با رشد داده بلند شد، فاصله را کم یا به روش افزایشی (oplog) مهاجرت کنید.
- **دفتر حذف‌ها**: `tombstones.ndjson` در همان مقصد (فقط شناسه‌ها، بدون داده شخصی) در لحظه حذف نوشته می‌شود تا پس از بازیابی پشتیبان قدیمی‌تر، داده حذف‌شده برنگردد (OPS-003).
- **ثبت**: `backup_records` و کارت «آخرین پشتیبان» در `/admin/settings`؛ نبود پشتیبان موفق در ۱۵ دقیقه هشدار بحرانی `backup_rpo` می‌دهد.

## ۵) بازیابی (OPS-005)
فقط در محیط آزمون تمرین و در محیط واقعی با تأیید مسئول:
1. `verifyBackup` (امضا + هش + رمزگشایی کامل) ← باید `ok` باشد.
2. بازیابی در پایگاه **خالی** (ابزار رد می‌کند اگر خالی نباشد) و دایرکتوری فایل جدید.
3. `runMigrations` روی پایگاه بازیابی‌شده.
4. `postRestoreChecks`: زنجیره حسابرسی، توازن دفتر کل و تطبیق پرداخت‌ها، بازپخش صف رویداد (idempotent)، ورود دفتر حذف‌ها و اعمال دوباره حذف‌ها.
5. فقط اگر همه سبز بود ترافیک را منتقل کنید؛ سپس worker را روشن کنید.
6. **تمرین**: `pnpm --filter @esp/api exec tsx scripts/backup-drill.ts [--ephemeral-key]` — گزارش RPO/RTO اندازه‌گیری‌شده در `docs/release/evidence/backup-drill-*.json`. تمرین فصلی توصیه می‌شود.

## ۶) رخدادها (runbook کوتاه)
| رخداد | اقدام |
|---|---|
| پایگاه از دست رفت | بند ۵؛ RTO هدف ۲ ساعت |
| صف dead-letter | `/admin/ops` ← بررسی علت ← replay تکی (consumerها idempotent‌اند) |
| ارائه‌دهنده قطع | circuit باز می‌شود و در `/admin/settings` «کند/قطع» دیده می‌شود؛ مسیر دستی مسابقه ادامه دارد |
| سوءاستفاده API شریک | `/admin/integrations` ← ابطال مشتری |
| نشت راز | `APP_SECRET` جدید، قدیمی در `APP_SECRET_PREVIOUS`، اجرای «چرخش رازها»، سپس حذف مقدار قدیمی؛ نشست‌ها پایان می‌یابند |
| دیسک بالای ۸۵٪ | هشدار `disk`؛ `BACKUP_KEEP` را کم یا فضا اضافه کنید؛ اجرای نگهداری |
